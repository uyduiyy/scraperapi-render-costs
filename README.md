## What "dynamic content" actually means (and why your request comes back empty)

Dynamic content is anything a page loads *after* the initial HTML arrives, usually pulled in by JavaScript running in your browser. Because the data isn't in the first response, a plain HTTP fetch comes back half-empty. On a modern React or Vue single-page app, that first response can literally be an empty `<div id="root"></div>` plus a few hundred kilobytes of JavaScript that builds the real page afterward.

Dynamic loading shows up in a handful of common forms:

- **AJAX requests** — the page fetches data in the background without reloading
- **Infinite scroll** — new items load as you scroll down
- **Lazy loading** — content only appears when it scrolls into view
- **WebSocket updates** — the page keeps a connection open and streams new data
- **Framework re-rendering** — React/Vue apps redraw the page in place as state changes

There's a quick way to confirm your target is dynamic: open DevTools, hit the Network tab, refresh the page, and compare. If the data shows up in an XHR response but not in the original HTML source, you're dealing with client-side rendering — and your plain HTTP request will never see it.

## Three ways to scrape dynamic content (and when each one breaks)

You have three realistic options. Two you run yourself; one you outsource.

**Option 1: Replay the site's internal API.** Nearly every page that fills itself with data sends XHR/fetch requests to a private backend endpoint returning JSON. Find that endpoint in DevTools (filter by Fetch/XHR, trigger the loading action, right-click the request, Copy as cURL), then replay it with the right headers and cookies. Done properly, this is tens of times faster than rendering and needs no browser at all. The catch: you need to reproduce CSRF tokens, session cookies, and sometimes `Authorization: Bearer` headers. If a token or request signature is generated by obfuscated JavaScript in the browser — or in WASM — reproducing it server-side is extremely hard, and that's your cue to switch approaches.

**Option 2: Run a headless browser yourself.** Selenium, Playwright, or Puppeteer executes the page's JavaScript just like a real visitor. The key skill is waiting correctly: in Playwright, `networkidle` means "wait until network traffic settles" and `wait_for_selector` means "wait until this element actually exists." For infinite scroll, you scroll to the bottom repeatedly, pause a couple of seconds each time, and stop when `document.body.scrollHeight` stops growing. This approach is the most universal, but it's slower by an order of magnitude, eats CPU and RAM, and — here's the part the tutorials gloss over — a browser farm you run yourself still gets fingerprinted and blocked by anti-bot systems, which means maintaining stealth patches, proxies, and CAPTCHA handling on top.

**Option 3: Outsource rendering to a scraping API.** This is where ScraperAPI sits. Instead of maintaining headless browsers and proxy pools, you send one request with `render=true` and their infrastructure handles the browser, the IPs, and the CAPTCHA walls.

## How ScraperAPI's `render=true` works

Set `render=true` and ScraperAPI fetches the page with a headless Google Chrome instance, returning fully rendered HTML. The feature is available on **all plans**, including Hobby — you don't need a premium tier just to render JavaScript.

There are three ways to pass the parameter, which matters when you're wiring it into existing code:

1. **URL parameter** — request `https://api.scraperapi.com` with `api_key`, your `url`, and `render=true`. Scrapy users can simply swap their `start_urls` for the ScraperAPI endpoint with `render=true` appended.
2. **Request headers** — set `x-sapi-render: true` along with `x-sapi-api_key`.
3. **Proxy mode** — route your requests through `proxy-server.scraperapi.com:8001` with `scraperapi.render=true` as the proxy username and your API key as the password. This is handy because any HTTP client that already supports proxies needs zero code changes.

One detail the docs call out for Scrapy users: don't set `DOWNLOAD_DELAY` and `RANDOMIZE_DOWNLOAD_DELAY` when going through the API. Those settings throttle your concurrency, and ScraperAPI's rotating proxy pool handles the rate-limiting side for you.

The official Python SDK works the same way: create a `ScraperAPIClient` with your key and call `client.get(url, render=true)`.

## The real cost: why 100,000 credits is not 100,000 pages

This is where most comparisons go quiet, and it's the single most useful thing to understand before picking a plan. ScraperAPI prices different domains by difficulty: a standard page costs 1 credit, but **Amazon costs 5, Google and Bing (including subdomains) cost 25, and LinkedIn costs 30**. Sites behind Cloudflare, Datadome, or PerimeterX add 10 credits per request when ScraperAPI bypasses them. Third-party pricing breakdowns put JS-rendered requests at roughly 10 credits each — so rendering multiplies your burn rate on top of whatever the domain costs.

Put together, the math looks like this on a Hobby plan (100,000 credits):

- Plain requests to ordinary pages: ~100,000 pages
- Amazon product pages: 100,000 ÷ 5 = 20,000 pages
- Amazon pages with `render=true`: at roughly 15 credits each (5 domain + ~10 render), about 6,600 pages
- Google SERP pages with rendering: at roughly 35 credits, under 3,000 pages

Two official tools keep this under control. The **Domain Cost Estimator** in your dashboard shows the exact credit cost for any URL before you commit, and the `max_cost` parameter lets you cap how much any single scrape can consume. If you're budgeting a project, run your target URLs through the estimator first — it's the difference between guessing and knowing how long your credits will actually last.

## Who ScraperAPI is not for

Saying this plainly saves everyone time. ScraperAPI is the wrong pick if:

- **Your targets are easy and unprotected.** If plain requests work, paying per credit for a scraping API is overhead. Grab a library like BeautifulSoup, replay the site's JSON endpoints directly, and spend the $49 on something else.
- **You need data, not HTML.** Every API in this category hands you rendered markup; parsing and selector maintenance stay on you. If a site restructures weekly and you don't want to babysit selectors, a fully managed data provider is a different (pricier) product category.
- **Your volume is tiny and permanent.** A 1,000-credit free plan covers light ongoing use, but if you consistently need a few thousand rendered requests monthly, do the estimator math first — Hobby only pays off once you're clearly past the free tier's ceiling.
- **Your hardest targets are the majority of your crawl.** With measured success in the low-to-mid 60s on protected sites, failed-and-retried requests eat credits. Mixed workloads are fine; a crawl that's 80% DataDome-walled is the scenario where specialists earn their premium.
